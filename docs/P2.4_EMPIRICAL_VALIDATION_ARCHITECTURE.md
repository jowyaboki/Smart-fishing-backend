# P2.4 Empirical Validation Architecture

## 1. System Overview

Milestone P2.4 introduces an Empirical Tide Validation Engine designed to statistically compare real-world hydrographic sea level observations against astronomical harmonic predictions produced by the `MoroccanHarmonicTideProvider`.

The primary architectural purpose of this engine is objective verification: providing rigorous mathematical error quantification (Bias, MAE, RMSE, Standard Deviation, Max Absolute Error, and Tidal Peak Errors) while guaranteeing that theoretical models are never silently altered without verified empirical justification.

```
                      +-----------------------------+
                      |   Hydrographic Repository   |
```

## 2. Component Structure

### 2.1 Domain Layer (`src/domain/tideValidationModels.ts`)
- **ValidationObservationPair**: Aligned comparison pair holding normalized observation value, astronomical predicted value, model residual ($e_i = \hat{y}_i - y_i$), vertical datum, and quality tier.
- **StatisticalMetrics**: Aggregated scalar metrics including Bias, MAE, RMSE, standard deviation of errors, maximum absolute error, and minimum absolute error.
- **PeakValidationMetrics & MatchedTidalPeak**: Extrema detection comparison pairing observed High/Low waters against astronomical High/Low predictions within temporal tolerance windows ($\pm 180$ minutes).
- **DataSuitabilityResult**: Multi-tier data suitability assessment (`SUITABLE`, `MARGINAL`, `UNSUITABLE`) evaluating observation count ($\ge 720$), duration ($\ge 29.53$ days), completeness, vertical datum matching, and provenance authenticity.
- **TideValidationRun**: Domain entity modeling an execution run, persisting statistical results, suitability scores, exclusion breakdown, and locked safety flags.

### 2.2 Mathematical Engine (`src/services/hydrographic/validationStatistics.ts`)
- Isolated mathematical functions without side effects or database dependencies.
- Independently verifiable formulas operating over standard JavaScript floating-point numbers with deterministic rounding.
- 3-point local extrema detector identifying turning points for High and Low water tides.

### 2.3 Empirical Validation Service (`src/services/hydrographic/empiricalValidationService.ts`)
- Retrieves observations from `HydrographicRepository`.
- Performs observation integrity filtering:
  1. Vertical datum conformance matching station reference datum.
  2. Physical bounds validation $[-2.0\text{m}, +12.0\text{m}]$.
  3. Strict provenance validation (`qualityTier === 'observed'`, `dataStatus === 'observation'`, `isSimulatedFallback === false`).
  4. Timestamp normalization and duplicate rejection.
- Obtains predictions from `MoroccanHarmonicTideProvider` for the exact coordinates and UTC timestamps.
- Evaluates data suitability criteria.
- Computes statistical and peak metrics.
- Enforces production safeguards (`status = 'NOT_VERIFIED'`, `isCalibrationEnabled = false`).
- Records the run in SQLite.

### 2.4 SQLite Persistence (`src/data/database.ts` & `src/data/hydrographicRepository.ts`)
- Dedicated table `tide_validation_runs` with foreign key referencing `hydrographic_stations(id)`.
- Index on `(station_id, executed_at_utc DESC)`.
- Full serialization of metrics, suitability reports, and exclusion reasons in JSON fields.

### 2.5 API Layer (`src/routes/hydrographicRoutes.ts` & `src/app.ts`)
- `GET /api/v1/hydrographic/stations`: List reference stations.
- `GET /api/v1/hydrographic/stations/:stationId`: Get station detail.
- `GET /api/v1/hydrographic/stations/:stationId/quality`: Station data quality report.
- `POST /api/v1/hydrographic/stations/:stationId/validate`: Trigger validation run.
- `GET /api/v1/hydrographic/stations/:stationId/validations`: Query past validation runs.
- `GET /api/v1/hydrographic/validations/:id`: Retrieve single validation run.

## 3. Production Safeguards

1. **Immutable Calibration Flag:** `isCalibrationEnabled` is strictly forced to `false`. Automated coefficient updates are prohibited.
2. **Empirical Status Classification:** In the absence of certified field gauge telemetry, runs default to `NOT_VERIFIED`.
3. **Simulated Fallback Exclusion:** Any observation tagged with simulated provenance or fallback markers is rejected from validation pairs.
4. **Android Client Independence:** Hydrographic validation routes are partitioned under `/api/v1/hydrographic/`, maintaining total backwards compatibility with mobile clients.
